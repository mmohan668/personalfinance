# Personal Finance PostgreSQL / Flyway migrations

## Layout

- `db/migration/versioned/1.0.0.0`: ordered, versioned schema and seed migrations.
- `db/migration/repeated`: repeatable functions, procedures, triggers and views.

## Flyway configuration

The supplied locations are retained. For a fresh database, prefer:

```yaml
spring:
  flyway:
    enabled: true
    locations:
      - classpath:db/migration/repeated
      - classpath:db/migration/versioned
    schemas: public
    validate-on-migrate: true
    table: flyway_schema_history_pf
    baseline-on-migrate: false
```

Flyway executes all pending versioned migrations before repeatable migrations. The order of the two locations does not make repeatables run before versioned migrations.

## Key changes made

1. Renamed the initial release migration to include the required `__` separator.
2. Moved template configuration DDL before `bulk_uploads_status`, because the latter references `template_name`.
3. Renumbered later grid and template metadata migrations to make the execution order explicit and unique.
4. Removed explicit `BEGIN` / `COMMIT` statements from grid seed migrations. Flyway manages migration transactions.
5. Changed `system_config` to use a composite `(config_value, user_id)` FK to `(id, user_id)` in `user_reference_value`, preventing cross-user configuration references.
6. Changed financial transaction subcategory FK to the simple `user_subcategories(id)` FK, in line with the agreed schema (no `admin_user_id` column or composite FK on `user_subcategories`).
7. Changed financial amount validation to `amount <> 0`, because the bulk transaction procedure stores expenses as negative values.
8. Reworked `initialize_new_user` to copy from canonical `reference_values`, not the nonexistent `system_reference_value`; it also sets Currency = INR and Date Format = dd/MM/yyyy using the user's own reference-value IDs.
9. Aligned the `users_history` deleted-status check with the `users` table's soft-delete constraint.
10. Added initial password-history capture for the bootstrap System account, since repeatable triggers are installed after versioned migrations.
11. Added indexes supporting history admin-user lookups, system-config reference ownership, financial-transaction FK checks, and grid personalization user lookups.
12. Renamed repeatable files to match their database objects and avoid duplicate prefixes.

## Important assumptions to verify

- `financial_transactions.admin_user_id` is treated as the transaction owner's user ID. The bulk procedure sets it to `p_user_id`; the composite location FK relies on this meaning. If `admin_user_id` is actually a separate administrator identity, the ownership model needs a deliberate redesign.
- `initialize_new_user` self-associates `admin_user_id = p_user_id`, matching the supplied implementation.
- Global canonical reference data is in `reference_values`. No migration in the supplied archive creates `system_reference_value`.
- The system account migration still contains `PASSWORD_HASH_TEMP`. Replace it with a hash generated by the same Spring Security password encoder before enabling authentication for that account. The script does not invent a usable password hash.
- The `users_history` trigger records INSERT and UPDATE; physical user deletion is not supported by the FK from history to users. Use soft deletion.
- `initialize_new_user` does not insert password history explicitly; the `AFTER INSERT` password trigger handles the INITIAL record.

## Deployment notes

- This package is intended for a fresh database, as confirmed by the project owner. Do not use it to replace versioned migration files in a database where the original migrations have already been applied.
- `baseline-on-migrate: false` is recommended for a new database. If adopting an existing schema, create and verify an explicit baseline instead of relying on automatic baselining.
- No explicit transaction control is included in migrations or procedures. Spring/Flyway should own transaction boundaries.
- Review and test the migrations against the exact PostgreSQL major version used by the application before production deployment.
